# 카드 매입 공제 검토 워크벤치 — 설계

작성 2026-11-22. 사용자 승인: 채팅에서 흐름 6단계 승인("가보자").

## 왜 만드나

공개 채용공고(세무 AI 플랫폼, 백엔드)를 읽고 "회사가 만들고 싶어 하는 것"을 작게 직접 구현해 면접에서 화면으로 시연하기 위함.
공고의 핵심 문장들을 실제로 돌아가는 기능으로 보여 주는 것이 목적이다.

- 업무 흐름·권한·Excel 산출물·세법 규칙을 먼저 모델링하고 그 위에 Agent + 사람 승인
- 초안·제안은 AI, 최종 판단은 사람, 사람과 Agent가 같은 권한·감사 기준
- 사람의 판단이 감사추적이자 다음 작업의 컨텍스트로 남음
- 조서 간 숫자 흐름, 다른 사용자 화면까지 실시간 반영
- Excel 손실 없는 왕복(업로드·검증·내보내기·재업로드·차이 비교)
- AI가 늦거나 실패해도 업무가 멈추지 않음
- 세무 Action을 Tool 계약으로 정의(MCP-ready), 평가를 코드로 관리


## 업무 한 포인트 (사용자 선택)

소상공인 부가세 신고 대행 시, 사업용 신용카드 매입을 거래별로 **매입세액 공제/불공제** 재확인하는 일.
홈택스 사전분류는 참고용이라 세무 담당자가 가맹점·업종·과세유형·용도로 다시 판단한다(조사 근거: README 출처).

불공제 사유(부가가치세법 제39조 제1항, 데모용 단순화):
- 비영업용 소형승용차 구입·임차·유지(제5호) — 고객 보유 차량이 소형승용차일 때 주유·정비·렌트. 경차·화물·9인승↑는 공제
- 기업업무추진비 및 유사 비용(제6호) — 거래처 접대, 선물
- 사업과 직접 관련 없는 지출(제4호) — 가사·개인 사용
- 면세사업 관련·토지 관련(제7호), 사업자등록 전 매입(제8호)
- 가맹점이 면세사업자이거나 간이과세자(영수증 발급 대상)인 경우 공제 대상 매입세액 없음

## 화면에서 보이는 흐름 (승인된 6단계)

1. 고객(가상 소상공인 "동네 베이커리") 카드 매입 엑셀 업로드 — 샘플 40건 내외
2. **규칙**이 확실한 건 판정(과세유형, 등록일 이전, 차량 업종 × 고객 차량 정보)
3. 애매한 건은 **로컬 LLM Agent**(Qwen3.6-35B-A3B, MLX)가 근거 조문·이유·확신도와 함께 제안
4. 담당자가 거래별 승인/수정(사유 필수) → 감사이력. 같은 가맹점이 다시 나오면 **이전 사람 판단을 근거로 먼저 제안**
5. 승인된 값이 **부가세 신고서 요약 조서**(신용카드 매입 공제 공급가액·세액, 불공제 사유별 합계)로 흐르고, 다른 사용자 화면에 실시간 반영
6. 결과 Excel 내보내기 → 수정본 재업로드 시 **차이 비교** 후 반영

## 목표 / 비목표 / 실패 조건

목표
- 면접관 앞에서 5분 안에 1→6을 끊김 없이 시연
- 공고 스택: NestJS + Fastify, MikroORM, Zod, PostgreSQL, GraphQL(Mercurius) + REST, Vitest
- 같은 Zod 스키마·서비스를 GraphQL과 REST가 공유(같은 권한·검증)
- 실제 DB 통합 테스트 + "보호 장치 빼면 실패" 확인(기존 tax-invoice-ledger 방식)

비목표
- 실제 세무 판단의 정확성 보장(데모용 단순화 명시), 실제 홈택스 연동, 다중 고객·다중 기간 완전 지원, 배포
- 대량 그리드 최적화, 오프라인 편집

실패 조건(동작해도 실패로 봄)
- 특정 회사 이름·로고·제품명 사용(사칭 금지). README에 "공개 채용공고를 읽고 해석한 개인 프로젝트"만 표기
- LLM이 꺼져 있으면 화면이 멈춤
- AI가 승인까지 해 버리는 경로가 존재
- 실제 개인·회사 데이터 사용(전부 가상 데이터)

## 정한 것 (사용자 결정)
- 업무 포인트: 카드 매입 공제/불공제 재확인
- LLM: 이 맥북의 로컬 Qwen 35B MoE(Qwen3.6-35B-A3B MLX), 외부 API 없음
- 제대로 만들고, 시연 가능해야 함
- 화면은 예쁘게: Meta 공개 디자인 시스템 **Astryx**(React 19 + StyleX, MIT, 베타) 사용
- Agent 엔진: 사내 AI Assistant에서 쓴 **Cline식 자율 루프**를 그대로 녹임
  - 모델이 매 턴 Tool 하나를 골라 XML 태그로 호출 → 코드가 Zod로 인수 검증·실행 → 결과를 다음 턴에 돌려줌 → `attempt_completion`으로 끝
  - 최대 단계 수 제한, 단계마다 진행 이벤트를 화면에 실시간 표시("거래 조회 → 이전 판단 확인 → 조문 확인 → 제안")
  - 되돌리기 어려운 Action(승인)은 Tool 목록에 없음 — Agent는 제안까지만
  - Cline(Apache-2.0)의 루프 구조를 참고해 TypeScript로 새로 구현, README에 출처 표기(코드를 직접 가져오면 LICENSE·NOTICE 포함)

## 빌더 재량 (내 판단으로 정함, 사용자 확인 전)
- 새 레포 `vat-workbench`(기존 tax-invoice-ledger는 별도 유지)
- 화면: React 19 + Astryx 0.7.11(theme-neutral, 공개 2주 지난 버전 고정) + TanStack Query, Vite 빌드 후 Fastify가 정적 서빙. Next.js는 시연 범위에 비해 무거워 제외. Astryx CLI `init`(AGENTS.md 자동 작성)은 실행하지 않고 문서를 직접 읽어 적용
- 실시간: Mercurius GraphQL subscription(거래 판정 변경, 요약 조서 변경)
- Agent 호출: mlx_lm.server(OpenAI 호환)를 HTTP로 호출. Tool 인수와 최종 제안은 Zod로 검증, 형식이 틀리면 오류를 돌려주고 다음 턴에 고치게 함(Cline 방식), 단계 초과·타임아웃 시 "검토 필요"로 떨어지고 규칙 결과만으로 업무 계속
- Agent도 actor(`agent:qwen`, 역할 preparer)로 기록 — 제안만 가능, 승인 불가
- Tool 계약: Zod로 정의한 세무 Action(거래 조회, 판정 제안, 이전 판단 조회)을 Agent가 사용. MCP stdio 서버 노출은 2단계
- Excel: exceljs. 내보낸 파일에 거래 ID·판정 칸 포함 → 재업로드 시 ID 기준 차이 계산
- 평가: 정답 라벨 30건 고정 세트, 정확도·지연 측정 스크립트, 모델 3종 비교표(2단계 가능)
